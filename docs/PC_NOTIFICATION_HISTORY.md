# PC 알림 이력 — 설계안

> 상태: **승인·구현 (2026-11-15, v0.26.0)** — 결정은 `DECISIONS.md` M-32. 아래는 승인 당시 설계안이며, 구현에서 바뀐 점: 목록 본문은 2,000자까지 자르고, 데이터 폴더 접근 제한은 서비스(LocalSystem)가 시작할 때 건다.
> 관련 결정: M-19(마스킹), M-28(알림 중계), M-29(PC↔PC), M-31(휴대폰 알림 이력)

## 1. 문제

휴대폰에는 알림 센터(M-31)가 있어 연결된 PC에서 온 알림을 나중에 다시 볼 수 있다. PC에는 같은 것이 없다.

| PC에 오는 알림 | 지금 PC에서 보이는 방식 | 나중에 다시 보기 |
|---|---|---|
| 휴대폰이 보낸 알림(알림 전달, M-28) | 트레이 풍선 알림 약 6초 | 불가 |
| 연결한 다른 PC의 Windows 알림(M-29 inbox) | 트레이 풍선 알림 약 6초 | 불가 |
| 이 PC의 감시 경보(이벤트 로그·워치독·개발 서버) | 휴대폰·Telegram으로만 나감 | DB `alert_log`에 기록은 되지만 보는 화면 없음 |
| 이 PC 자신의 Windows 알림 | Windows가 직접 띄움 | Windows 알림 센터 |

자리를 비웠거나 풍선을 놓치면, PC에서는 그 알림을 다시 찾을 방법이 없다. 휴대폰 알림 센터에서 볼 수는 있지만, 다른 기기에서 온 알림을 보려고 PC 앞에서 휴대폰을 꺼내야 한다.

**성공 기준**: PC 앞에서 놓친 알림(다른 기기에서 온 것, 이 PC의 경보)을 트레이에서 바로 다시 찾을 수 있다. Agent를 재시작한 뒤에도 남아 있다.

## 2. 지금 구조에서 확인한 사실

- 다른 기기에서 온 알림은 경로가 둘(휴대폰 → `POST /api/v1/notifications`, 연결한 PC → inbox 롱 폴링)이지만, 모두 `NotificationForwardingService.AcceptFromDeviceAsync` **한 곳**을 지난다. 여기서 중복(`id`)을 거르고 마스킹(M-19)한 뒤 트레이 풍선(`toast.show`)과 푸시로 보낸다. 기록 지점은 이 메서드 하나면 된다.
- 중계는 Windows 알림 전달이 켜져 있을 때만 동작한다(`DeviceHub.CanRelay`). 꺼져 있으면 중계 알림이 PC에 오지 않으므로 이력도 없다.
- 허브의 `NotificationInbox`는 연결한 PC에 넘겨주기 위한 메모리 버퍼(200건·30분)라서 이력으로 쓸 수 없다.
- 감시 경보는 `AlertDispatcher`가 이미 `alert_log`(SQLite)에 상태와 함께 기록한다. 지우는 코드가 없어 계속 쌓인다.
- `notification_event` 테이블은 V1에서 만들어 두었지만 쓰는 코드가 없다. 열이 이 PC Windows 알림의 필터 판정용(`sensitivity`, `forwarded`, `dropped_reason`)이고, 보낸 기기 정보가 없다.
- DB는 `%ProgramData%\Homebase\data\localops.db`이고 스키마는 V1이다. 마이그레이터는 `version < 1`만 확인하므로, 표를 더하는 V2는 옛 Agent로 되돌려도 깨지지 않는다.
- 트레이는 Agent와 모바일 브리지 파이프(`MobileBridge`)로 요청·응답·푸시를 주고받는다. 파이프 ACL은 SYSTEM·Administrators·로그인 사용자다.

## 3. 제안

### 3.1 무엇을 보여 주나

| 범주 | 포함 | 근거 |
|---|---|---|
| 다른 기기에서 온 알림(휴대폰·연결한 PC) | **포함** | 핵심. 지금 풍선 6초뿐이다. |
| 이 PC의 감시 경보 | **포함**(새로 저장하지 않고 `alert_log`를 읽음) | 이미 기록되고 있어 비용이 작다. PC 앞에서 "무슨 경보가 나갔나"를 볼 수 있다. |
| 이 PC 자신의 Windows 알림 | **제외** | Windows 알림 센터가 이미 보여 준다. 저장하면 메신저 본문이 PC에 한 벌 더 남는다. |

### 3.2 어디에 저장하나 — Agent(SQLite)

V2 마이그레이션으로 새 표를 하나 만든다.

```sql
CREATE TABLE notification_history (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  notif_id TEXT,              -- 중계 id(있으면). 같은 알림을 두 경로로 받아도 한 번만
  origin_id TEXT NOT NULL,    -- 기기 id 또는 hub:<pcId>:<origin>
  origin_name TEXT NOT NULL,  -- "Galaxy S24", "DESKTOP-…"
  origin_kind TEXT NOT NULL,  -- phone | pc
  app TEXT NOT NULL,
  title TEXT NOT NULL,        -- 마스킹된 값
  body TEXT,                  -- 마스킹된 값
  ts TEXT NOT NULL,           -- 기기가 알림을 만든 시각
  received_at TEXT NOT NULL
);
CREATE INDEX ix_notification_history_received_at ON notification_history(received_at);
```

- **쓰기**: `AcceptFromDeviceAsync`에서 중복을 거르고 마스킹한 직후, 풍선을 띄우기 전에 한 줄 넣는다. DB 쓰기가 실패해도 중계(풍선·푸시)는 그대로 진행하고 오류만 로그에 남긴다.
- **보관**: 30일·최대 500건(휴대폰 M-31과 같음). Agent가 하루 한 번 정리한다. 같은 정리에서 `alert_log`도 30일보다 오래된 것을 지운다(지금은 무제한으로 쌓임).
- **보호**: 마스킹된 값만 저장한다. DB 파일은 ProgramData 아래이고 서비스(SYSTEM)만 쓴다. 착수 시 `data\` 폴더 ACL이 SYSTEM·Administrators로 제한되는지 확인하고, 아니면 `MobileDeviceStore`처럼 제한한다. 본문을 따로 암호화하지는 않는다. DPAPI LocalMachine은 같은 PC의 다른 프로세스를 막지 못해, 실익이 파일 ACL과 거의 같다.

트레이(사용자별 파일)에 저장하는 방식은 기각한다. 중계 알림은 아무도 로그인하지 않았을 때도 Agent에 오고, 그때는 트레이가 없으므로 그 알림이 이력에서 빠진다.

### 3.3 트레이 화면

- **트레이 메뉴**에 "알림 센터"를 추가한다. 안 읽은 것이 있으면 "알림 센터 (3)"처럼 개수를 붙인다. 대시보드 상단에도 같은 개수를 작게 표시한다.
- **알림 센터 창**(WPF, 기존 `ThemedWindow`):
  - 날짜별 목록. 한 줄 = 시각 · 보낸 기기 · 앱 · 제목. 누르면 본문 전체를 펼친다.
  - 위쪽 필터 칩: 전체 / 기기별 / "이 PC 경보".
  - "모두 지우기"(확인 창). 개별 삭제는 MVP에서 뺀다.
  - 창을 열면 그때까지 받은 것이 모두 읽음이 된다. `lastSeenAt` 하나를 사용자별로 `%LOCALAPPDATA%\Homebase`에 저장한다(휴대폰과 같은 규칙).
- **풍선 알림을 누르면** 알림 센터 창이 열린다.

### 3.4 Agent ↔ 트레이 (브리지 연산 추가)

| 연산 | 방향 | 내용 |
|---|---|---|
| `history.list` | 요청 → 응답 | `{before?, limit≤100}` → 중계 알림과 `alert_log`를 시간 역순으로 합친 목록 |
| `history.clear` | 요청 → 응답 | 중계 알림 이력을 모두 지운다. `alert_log`는 지우지 않는다(진단용) |

새 알림 도착은 기존 `toast.show` 푸시로 알 수 있으므로 별도 푸시 연산은 만들지 않는다. 트레이는 `toast.show`를 받을 때 안 읽은 개수를 1 올리고, 창이 열려 있으면 목록을 다시 읽는다.

### 3.5 하지 않는 것

- 휴대폰 이력을 PC에서 보거나, PC 이력을 휴대폰에 동기화하기. 각 기기는 자기가 받은 것만 보여 준다.
- 이 PC 자신의 Windows 알림 기록(3.1).
- 검색, 개별 삭제, 내보내기. 쓰임을 본 뒤에 판단한다.

## 4. 대가와 위험

- **같은 PC를 쓰는 다른 Windows 사용자도 볼 수 있다.** 이력 창은 로그인한 사용자 누구나 연다. 하지만 중계 알림은 지금도 로그인한 사용자에게 풍선으로 뜨고, 기기 페어링 자체가 PC 단위(사용자 단위가 아님)라서 노출 범위는 지금과 같다.
- **본문이 PC에 30일 남는다.** 지금은 메모리에 30분만 있었다. M-31에서 PC 보관을 기각한 이유 중 하나다. 이번 제안은 그 결정을 일부 뒤집는 것이고, 마스킹·파일 ACL·30일 제한으로 줄인다. 이 부분이 승인받아야 할 핵심이다.
- **첫 V2 마이그레이션이다.** 표만 더하므로 롤백은 안전하다. 다만 이후 설계 번들의 V2(GOAL-05)와 번호가 겹치므로, 그쪽을 착수할 때 V3로 옮겨야 한다.
- 중계가 꺼져 있으면(Windows 알림 전달 꺼짐) 이력도 비어 있다. 창의 빈 화면에 그 이유와 설정 위치를 안내한다.

## 5. 검증 계획

- **단위 테스트**: 마이그레이션 V1→V2, 저장·중복 id 무시·30일/500건 정리, `history.list` 병합 순서·페이지, DB 실패 시에도 중계가 계속되는지.
- **통합 테스트**: 기존 `HubLinkEndToEndTests`(루프백 Agent 두 대)에 "B가 보낸 알림이 A의 이력에 한 번만 남는다"를 추가한다.
- **실제 PC**: 에뮬레이터 앱(알림 전달 켬) → 이 PC에 중계 → 풍선이 사라진 뒤 트레이 알림 센터에 남는지 확인 → Agent를 재시작한 뒤에도 남는지 확인. 밤에는 `notify.test`를 쓰지 않는다.

## 6. 규모

Agent(V2 마이그레이션, 저장소, 정리, 브리지 연산 2개), 트레이(창 1개, 메뉴·대시보드 개수), 테스트. 앱·모바일 프로토콜 변경은 없다. 한 PR, 마이너 버전 하나(v0.26.0) 규모다.

## 7. 결정이 필요한 것

1. **본문을 PC에 30일 보관하는 것(M-31 일부 번복)을 받아들이는가.** 받아들이지 않으면 제목만 저장하거나, 보관을 24시간으로 줄이는 방안이 있다.
2. **이 PC의 감시 경보를 같은 창에 넣는가**(제안: 넣음).
3. **보관 30일·500건**이 적당한가.
