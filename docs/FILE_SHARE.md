# 파일·이미지 공유 (클립보드·파일 공유 2단계) — 설계안

> 상태: **승인 (2026-11-19, 권장 기본값대로) · 2a 구현 v0.50.0** — 결정 `DECISIONS.md` M-64. 2b는 다음 PR.
> 2a 구현에서 정한 것:
> - 파일별 SHA-256은 시작이 아니라 `done`에 싣는다. 휴대폰이 파일을 두 번 읽지 않고 올리면서 셀 수 있게 하기 위해서다.
> - 한도는 아직 코드 상수다(설정은 나중에).
> - 조각 차례는 30초 기다린 뒤에 503을 준다.
> - 본문 읽기 제한 시간 120초는 모든 경로에 둔다.
> - 아무도 로그인하지 않았을 때의 알림 문구는 휴대폰 알림에 둔다.
> 바탕: [`CLIPBOARD_SHARE.md`](CLIPBOARD_SHARE.md)(전체 로드맵, §4.3~4.5의 파일 부분), 1단계 결정 M-62(키 합의·트레이 확인)·M-63.

## 1. 요구와 성공 기준

요구(사용자): 클립보드 텍스트(1단계, v0.49.0)에 이어 이미지·파일을 주고받는다.

**성공 기준**
- 휴대폰 갤러리·파일 앱의 사진·문서를 공유 메뉴로 PC에 보내면, PC의 `다운로드\Homebase`에 저장된다. 사진 한 장이면 PC 클립보드에도 들어간다.
- PC의 파일과 캡처한 그림을 트레이에서 휴대폰·다른 PC로 보낸다. 휴대폰에서는 사진이 갤러리에, 그 밖의 파일은 `Download/Homebase`에 저장된다.
- 수백 MB도 보낼 수 있다. 화면을 끄거나 앱을 나가도 이어지고, 경로가 바뀌면(Wi-Fi ↔ LTE) 끊긴 곳부터 다시 보낸다.
- 1단계 원칙을 그대로 지킨다.
  - 내용은 기기·PC 쌍의 합의 키로 종단 암호화한다.
  - SYSTEM은 사용자 경로를 다루지 않는다.
  - 받은 실행 파일은 Windows가 경고한다.
  - 보내지 않는 동안 부담이 0이다.

## 2. 1단계에서 확인한 것 — 설계안(§4.3~4.5)에서 바뀌는 점

| 설계안의 전제 | 실제 | 2단계에 미치는 영향 |
|---|---|---|
| 파일 본문을 디스크로 흘려 쓰는 "스트리밍 HTTP"가 필요 | `MiniHttp`는 본문을 메모리에 한 번에 읽는다. 경로별 한도와 "인증 먼저" 패턴은 1단계 `/api/v1/clip`(1MiB)에서 이미 쓴다 | **4MiB 조각**이면 그대로 쓸 수 있다. 바뀌는 것은 셋뿐이다: 조각 경로의 한도(4MiB + 16), 본문 읽기 제한 시간(지금은 없음), 바이너리 응답 쓰기(지금은 JSON만). 동시 조각 수는 제한한다 |
| 조각마다 AES-GCM, 키는 토큰에서 | 키는 기기·PC 쌍의 ECDH 합의 키다(M-62). 키가 없거나 맞지 않을 때 다시 합의하는 흐름도 이미 있다 | 전송마다 하위 키를 만들고 위치 기반 nonce를 쓴다(§4.2). 키 합의 코드를 그대로 쓴다 |
| 휴대폰 큰 전송에는 포그라운드 서비스가 필요하고, 그러면 Play 신고를 감수해야 한다 | 앱은 이미 플랫폼 JobScheduler를 쓴다(M-22·M-27). Android 14부터는 **사용자 시작 데이터 전송 잡**이 있다 | 포그라운드 서비스 없이 잡으로 한다(§4.5, 결정 1) |
| 공유 메뉴로 받은 파일을 나중에 읽는다 | 공유 인텐트의 URI 읽기 권한은 받은 화면에 묶인다. 화면이 닫히면 잃을 수 있다 | `JobInfo.Builder.setClipData(…, FLAG_GRANT_READ_URI_PERMISSION)`로 권한을 잡에 넘긴다(API 26+). 파일을 복사해 두지 않는다 |
| 트레이가 받은 것을 클립보드에 넣는다 | 1단계에서 "트레이가 실제로 넣었다고 답해야 성공"(`clip.done`)으로 정했다 | 파일도 트레이가 저장을 마쳤다고 답해야 "받음"으로 친다. 트레이가 없으면 PC가 24시간 보관해 두었다가 넘긴다 |

## 3. 범위

| | 2a: 휴대폰 → PC | 2b: PC → 휴대폰 · PC → PC |
|---|---|---|
| 보내는 곳 | 공유 메뉴(모든 형식, 여러 개), 빠른 설정 타일(클립보드의 이미지) | 트레이 "파일 보내기…", "클립보드 보내기"(그림·탐색기에서 복사한 파일 목록까지) |
| 전송 | 휴대폰이 PC로 올림(잡, 이어 보내기) | 휴대폰: 푸시 알림 → 휴대폰이 받아 감(잡, 이어받기). PC → PC: Agent가 상대 PC로 올림 |
| 받는 쪽 | 트레이가 `다운로드\Homebase`에 저장 + MOTW. 사진 한 장이면 클립보드에도 | 휴대폰: 갤러리(사진)·`Download/Homebase`(그 밖). 다른 PC: 2a와 같음 |
| 새 Agent 코드 | 전송 저장소, 조각 경로, `Homebase.Transfer` 파이프(Agent → 트레이) | 트레이 → Agent 파이프 방향, 휴대폰용 조각 내려 주기, `share` 푸시, PC → PC 올리기 |

나중 단계(3단계)로 미루는 것: 탐색기 "보내기" 메뉴, 끌어다 놓기, 전송 목록 화면, 휴대폰 ↔ 휴대폰 중계, 폴더째 보내기.

## 4. 제안

### 4.1 전송 단위와 한도

- 한 번의 전송 = 파일 1~20개. 파일은 **4MiB 조각**으로 나눈다(Cloudflare 무료 요금제의 요청 100MB 제한과 휴대폰 메모리를 함께 고려).
- 기본 한도(Agent 설정, 결정 4)
  - 파일당 2GiB, 한 번에 4GiB.
  - 받는 PC의 전송 폴더는 10GiB까지 쓴다. 남는 디스크가 (전송 크기 + 2GiB)보다 작으면 507 `insufficient_storage`.
  - 끝나지 않았거나 아무도 가져가지 않은 전송은 24시간 뒤 지운다.
- 동시에 처리하는 조각은 4개까지다. 넘으면 503 `busy` + `Retry-After: 2`를 주고, 보내는 쪽이 잠시 뒤 같은 조각을 다시 보낸다.
- 조각 본문 읽기 제한 시간은 120초다(4MiB ÷ 0.5Mbps ≈ 67초). 지금 본문 읽기에 제한 시간이 없어, 느린 연결이 소켓을 계속 붙잡을 수 있는 문제도 함께 막는다.

### 4.2 암호화 (M-62 키 위에)

- **전송 키** = HKDF-SHA256(IKM = 기기·PC 합의 키, salt = 0 32바이트, info = `"homebase transfer v1"` ‖ 전송 id(16바이트), 32바이트).
  - 전송마다 다른 키라서 nonce를 위치로 정할 수 있다.
  - **nonce** = 파일 번호(4바이트) ‖ 조각 번호(8바이트), 빅엔디언.
  - 같은 키로 같은 nonce가 다시 쓰이지 않고, 조각을 바꿔치기하거나 순서를 섞으면 열리지 않는다.
- **조각 본문** = AES-256-GCM(평문 조각) = 암호문 ‖ 태그(16)이다. nonce를 싣지 않으므로 4MiB + 16바이트다.
- **메타데이터**(파일 이름·크기·MIME·SHA-256)도 이름이 민감할 수 있어 1단계 봉투(`{schema, id, nonce, data}`, 합의 키)로 봉인한다.
- **잘림 방지**: 받는 쪽은 메타데이터의 크기와 SHA-256을 마지막에 확인한다. 크기로 마지막 조각 번호가 정해지므로, 조각을 빼거나 덧붙이면 맞지 않는다.
- **픽스처**: `transfer-chunk.v1.json`(고정 합의 키·전송 id로 만든 조각 둘)을 .NET이 만들고 Kotlin이 연다. 1단계의 `clip-key.v1.json` 키를 그대로 쓴다.

### 4.3 프로토콜 (Mobile Protocol v1에 추가, `schema` 1 유지)

경로는 1단계처럼 고정 경로 + 쿼리로 둔다(라우터가 `head.Path` 전체 비교다).

| 메서드 | 경로 | 쓰는 쪽 | 내용 |
|---|---|---|---|
| POST | `/api/v1/transfer` | 기기 → PC | 봉투(메타데이터) → 200 `{schema, id, chunkBytes, have}` · 409 `clip_key_needed` · 413 `too_large` · 507 `insufficient_storage` |
| POST | `/api/v1/transfer/chunk?id=&f=&n=` | 기기 → PC | 바이너리 조각(토큰 확인 뒤 4MiB + 16까지 읽음) → 200 · 400(열리지 않음) · 409 `unknown_transfer` · 503 `busy` |
| GET | `/api/v1/transfer?id=` | 둘 다 | `{schema, have: [[파일별 받은 조각 번호 구간]], state}` — 끊긴 뒤 이어 보내기·이어받기 |
| POST | `/api/v1/transfer/done?id=` | 기기 → PC | SHA-256 확인 → 200 `{schema, saved}`. `saved`: `tray`(저장됨) · `waiting`(로그인한 사용자 없음, 24시간 보관) · 409 `hash_mismatch` |
| GET | `/api/v1/transfer/chunk?id=&f=&n=` | PC → 휴대폰 (2b) | 바이너리 조각(`application/octet-stream`) — PC가 그 휴대폰 키로 그때 봉인 |
| DELETE | `/api/v1/transfer?id=` | 둘 다 | 취소. 받는 쪽은 조각을 지운다 |

- **PC → 휴대폰 알림**(2b): 푸시 `{schema, kind: "share", pcId, id, nonce, data}`. 봉인한 내용은 `{schema, transferId, files: [{name, size, mime}], totalBytes, ts}`이고 TTL은 24시간(파일은 PC가 24시간 보관)이다. 보내기 한 번이 푸시 1건이다.
- **지원 여부**: 휴대폰은 `features`에 `share`를 더한다. PC는 404이면 "그 PC를 업데이트"로 보인다.
- 오류 응답은 지금처럼 `{schema, error, message}`다. `MiniHttp.Reason`에는 409·413·507을 더한다(지금은 "Error"로 나간다).

### 4.4 PC 안: Agent ↔ 트레이

- **원칙(설계안 §4.4)**: Agent(SYSTEM)는 사용자가 고른 경로를 열지 않고 사용자 폴더에 쓰지 않는다.
- **전송 폴더**: `ProgramData\Homebase\transfers\<id>\`(SYSTEM·Administrators 전용, M-32 방식). 받은 조각은 복호화해 평문으로 쓰고, SHA-256은 이어 가며 센다.
- **바이트 통로**: 새 파이프 `Homebase.Transfer`를 둔다. ACL은 `TrayPipeSecurity`와 같다. 프레임은 4바이트 길이 + 1바이트 종류 + 내용(JSON 머리 또는 원시 바이트, 최대 1MiB)이다. JSON 브리지에 base64를 싣지 않고, 전송 중에도 브리지(실시간 보기·승인)를 막지 않는다.
- **받기(2a)**
  1. Agent가 `done`을 확인하면, 브리지로 트레이에 `transfer.ready {id, from, files}`를 보낸다.
  2. 트레이가 `Homebase.Transfer`로 바이트를 읽어 `다운로드\Homebase\`에 쓴다. 다운로드 폴더는 Known Folder로 찾는다(사용자가 옮겼을 수 있음).
  3. 트레이가 `transfer.saved {id, ok, paths}`로 답하면 Agent가 폴더를 지운다. 1단계 `clip.done`과 같은 방식이다.
- **트레이가 없을 때**: Agent가 24시간 보관한다. 트레이가 붙으면 `transfer.pending`으로 넘겨, 로그인 뒤 저장되고 풍선이 뜬다.
- **보내기(2b)**: 트레이가 사용자 권한으로 파일·클립보드 그림을 읽어 `Homebase.Transfer`로 Agent에 흘려 넘기고, Agent는 자기 폴더에 둔다.
  - 휴대폰이 대상이면 `share` 푸시를 보내고, 휴대폰이 조각을 받아 가게 한다.
  - PC가 대상이면 Agent가 상대 PC에 기기로서 올린다(그룹 링크 토큰, 1단계 `SendToPcAsync`와 같은 재합의).
  - 진행 상황은 브리지 `transfer.progress`로 알린다.
- **클립보드에서 보내기(2b)**: "클립보드 보내기"가 클립보드 내용에 따라 보낸다.
  - 텍스트는 지금처럼 보낸다.
  - 그림은 PNG로 보낸다(`PNG` 형식이 있으면 그대로, 없으면 DIB를 PNG로).
  - 탐색기에서 복사한 파일 목록(`CF_HDROP`)은 그 파일들을 보낸다.

### 4.5 휴대폰: 백그라운드 전송 (결정 1)

- **Android 14 이상**: 사용자 시작 데이터 전송 잡(`setUserInitiated(true)`, 권한 `RUN_USER_INITIATED_JOBS`)을 쓴다.
  - 시간 제한 없이 진행 알림을 띄우고 이어 간다.
  - 화면이 보일 때만 예약할 수 있는데, 공유 메뉴·[받기] 알림 탭에서 시작하므로 맞는다.
- **Android 8~13**: 일반 잡(`setClipData`로 URI 권한 전달, 네트워크 조건)을 쓴다.
  - 한 번에 약 10분 실행되고, 끊기면 다시 예약돼 남은 조각부터 이어 간다.
- 포그라운드 서비스를 쓰지 않으므로 Play Console의 포그라운드 서비스 용도 신고가 필요 없다. 사용자 시작 잡이 별도 신고 대상인지는 착수 전에 Play 정책 문서로 다시 확인한다.
- **모바일 데이터**: 합계 20MB가 넘으면 보내기 전에 "모바일 데이터로 보낼까요?"를 묻는다. 잡에는 기본으로 "아무 네트워크"를 쓴다.

### 4.6 받은 파일 다루기

- **PC 쪽 (설계안 §4.5 그대로)**
  - 이름을 정리한다. 경로 구분자, `..`, 예약 이름, 끝의 점·공백, 제어·방향 바꿈 문자를 지우고 255자로 자른다. 같은 이름이 있으면 `이름 (2).확장자`로 저장한다.
  - `Zone.Identifier`(ZoneId=3)를 붙인다.
  - 자동으로 열지 않는다. 풍선은 "Galaxy S24에서 사진 3장 (12.4MB) — 다운로드\Homebase"로 띄우고, 누르면 폴더를 연다.
  - 사진 한 장이면 클립보드에도 넣는다(결정 3, `PNG` + 비트맵 두 형식).
  - PC 알림 센터에 "받은 파일" 항목을 메타데이터만(이름·크기·보낸 기기) 남긴다.
- **휴대폰 쪽**
  - API 29 이상은 MediaStore에 쓰는 중(`IS_PENDING`) 항목으로 조각마다 쓰고, 끝나면 공개한다. 사진·동영상은 `Pictures/Homebase`, 그 밖은 `Download/Homebase`에 둔다. 권한은 필요 없다.
  - API 26~28은 앱 전용 폴더에 두고 [열기]·[공유]만 단다.
  - 받기 알림: "집 PC에서 사진 2장 (4.1MB) [받기]". 작은 전송(합계 25MB 이하, 와이파이)은 묻지 않고 받는다(결정 2).
  - 끝나면 알림이 [열기]·[공유]로 바뀐다.

### 4.7 하지 않는 것 (2단계)

- 폴더째 보내기·동기화, 전송 목록 화면, 탐색기 "보내기" 메뉴, 끌어다 놓기는 3단계로 미룬다.
- 휴대폰 클립보드에 이미지를 넣는 것도 미룬다. 붙여 넣기를 받는 앱이 적어서, 갤러리 저장으로 대신한다.
- 포그라운드 서비스는 쓰지 않는다(§4.5).

| PR | 범위 | 규모 | 확인 |

## 6. 대가와 위험

- **Cloudflare 경로**: 4MiB 조각이라 크기 제한에는 걸리지 않는다. 하지만 느리고, 큰 파일을 상시 흘리는 사용은 권하지 않는다. 앱에 "Cloudflare 경로 — 느릴 수 있음"을 표시한다(결정 5).
- **인터넷에 열린 쓰기 경로가 커진다**: 조각 경로는 인증 먼저, 한도·동시 수·읽기 제한 시간·디스크 여유 확인으로 지킨다. 보안 리뷰 대상이다.
- **디스크**: 받는 PC는 전송 폴더와 다운로드 폴더에 잠깐 두 벌을 둔다(트레이 저장 뒤 전송 폴더는 지움).
- **휴대폰 잡**: 제조사 배터리 정책이 일반 잡(Android 13 이하)을 미룰 수 있다. 이어 보내기로 잃지는 않지만 늦을 수 있다.
- **버전**: 양쪽 모두 새 버전이어야 한다. 옛 앱은 `share`를 등록하지 않아 대상에 나오지 않고, 옛 PC는 404를 준다.
- **로컬 빌드 불가**: 이 PC에는 Android SDK가 없다. 앱은 PR CI와 실기로만 확인할 수 있어, 1단계처럼 CI가 첫 컴파일이다.

## 7. 결정이 필요한 것

1. **휴대폰 백그라운드 전송**: Android 14 이상은 사용자 시작 전송 잡, 그 아래는 일반 잡 + 이어 보내기(포그라운드 서비스 없음, Play 신고 없음) — 권장. 대안은 포그라운드 서비스(`dataSync`, Play 신고·영상 필요)나 앱 화면에서만 전송이다.
2. **휴대폰 자동 받기**: 합계 25MB 이하·와이파이면 묻지 않고 받고, 그 밖은 [받기] — 권장. 대안은 항상 묻기다.
3. **PC에서 받은 사진 한 장을 클립보드에도 넣기**: 켬 — 권장.
4. **한도 기본값**: 파일당 2GiB, 한 번에 4GiB, 전송 폴더 10GiB, 24시간 보관 — 권장.
5. **Cloudflare 경로의 큰 파일**: 허용하고 "느릴 수 있음" 표시 — 권장. 대안은 100MB 넘으면 Cloudflare로 보내지 않기다.
6. **순서**: 2a(휴대폰 → PC)부터 — 권장. 휴대폰 사진을 PC로 옮기는 쪽이 더 자주 쓰일 것으로 본다.
